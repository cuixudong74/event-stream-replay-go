# event-stream-replay-go

面向事件流的重放与重处理能力。事件持续写入本地追加存储（`Store`），下游（`Sink`）
依据事件维护派生结果。当处理逻辑调整或下游结果出现偏差时，可选取历史区间重新处理，
并把新结果投递回下游，同时不影响正在进行的实时处理。

## 架构

```
                 ┌──────────────┐
  事件写入 ─────▶│ Store (追加)  │◀─────────────┐
                 └──────┬───────┘              │
                        │ 按位置区间读取         │
        ┌───────────────┼───────────────────┐  │
        │               │                   │  │
  LiveProcessor    Replayer(job A)     Replayer(job B)
  (实时通道)        (下游甲的重放)        (下游乙的重放)
        │               │                   │
        ▼               ▼                   ▼
     Sink 甲         Sink 甲             Sink 乙     ← 幂等写入
        │               │                   │
  CheckpointStore: 每通道一个检查点，原子写（tmp+fsync+rename）
```

- **Store**：追加式存储，每条事件分配单调递增位置 `Pos`（从 0 开始），
  `Read(from, to)` 返回闭区间内的全部事件。
- **Sink**：下游接口 `Apply(ctx, Delivery) (Result, error)`，必须幂等。
  `MemSink` 是内置的幂等实现，按事件 ID 去重。
- **Replayer**：无状态重放器，进度全部落在 `CheckpointStore`，
  因此多下游、多副本可共享同一实现而互不干扰。
- **LiveProcessor**：实时通道，尾随存储投递新事件，独立检查点。
- **CheckpointStore**：文件持久化，`tmp + fsync + rename` 原子替换，
  崩溃后要么旧值要么新值，不留部分写入。

## 重放语义

### 区间精确性
`Replay(ctx, id, sink, from, to, cfg)` 覆盖且仅覆盖闭区间 `[from, to]` 内的事件，
两个端点都生效，不多算不漏算。区间内某位置尚未写入时（实时尚未到达），
重放会等待而不是跳过。

### 与实时处理并发
重放与实时是两条独立通道（不同 channel 名、不同检查点）。重放期间新到达的
事件由实时通道正常处理，不丢不跳。同一事件若被两条通道都投递，由 Sink 幂等
去重，因此两条通道结束后，下游状态与对完整历史做一次全量重放一致。

### 幂等与重复投递原因
Sink 按事件 ID 去重，重复投递返回可区分的原因：

| Reason               | 含义                                             |
|----------------------|--------------------------------------------------|
| `applied`            | 首次应用                                          |
| `duplicate_retry`    | 同一通道内重复（重试、重放恢复后重发在飞批次）      |
| `duplicate_replay`   | 另一通道已应用过（实时与重放覆盖同一事件）          |

无论哪种重复，派生结果都只累计一次。

### 中断与恢复
- 提交粒度为批次（`BatchSize`）：一批全部投递成功后才原子推进检查点。
- 中断（取消/超时/进程崩溃）后，检查点停留在最近一个已提交批次末尾；
  在飞批次会被重发，由 Sink 幂等去重，不重复累计、不跳过任何事件。
- 检查点带 `Done` 标志：进程重启后可区分"未完成的重放"（可恢复）与
  "已完成的重放"（直接返回）。用同一 `replayID` 再次调用 `Replay` 即从
  `Committed+1` 继续。

### 多下游独立进度
每个下游用各自的 `replayID`（检查点通道 `replay:<id>`）重放同一份事件流，
进度独立持久化，随时可用 `Replayer.Progress(replayID)` 查询。各重放运行在
各自 goroutine 与限速器下，单个下游变慢不阻塞其他下游，也不拖慢实时通道。

### 速率与并发配置（`ReplayConfig`）

| 字段          | 默认 | 说明                                                     |
|---------------|------|----------------------------------------------------------|
| `RatePerSec`  | 不限 | 每秒投递上限，防止压垮下游或挤占实时链路                   |
| `Concurrency` | 1    | 批次内并发投递协程数；结果按下标回填，与位置顺序一致        |
| `BatchSize`   | 64   | 提交粒度（也是取消时的对齐边界）                            |
| `Seed`        | 0    | 供投影逻辑派生逐事件确定的随机源（如 `seed ^ pos`）         |

取消/超时通过 `ctx` 控制：重放在批次边界停止并返回 `ctx.Err()`，
检查点位置明确，下游因幂等不会停在中间状态；同一 `replayID` 重启即可继续。

### 确定性
固定输入、固定 `Seed` 下，同一区间的重放结果逐条可复现：
`ReplaySummary.Decisions` 按位置升序记录每条事件的判定结论，
两次运行的 Decisions 与下游最终状态完全一致（并发只影响时序，不影响结果，
因为结果按下标回填且 Sink 幂等判定与顺序无关）。

## 测试

```sh
go test -race ./...
```

覆盖：区间边界（含单点/全量区间）、重放与实时并发、重复投递原因、
中断恢复（含跨"进程重启"）、检查点原子写、多下游独立进度、
取消/超时与限速、固定种子下的逐条可复现性。
